## Отличия от проекта

1. **P3m — контрольная проба без X25519MLKEM768 (нового в проекте нет).** Когда клиент сам
   X25519MLKEM768 не шлёт, а эталон (fp chrome) прошёл, приложение повторяет ту же попытку с
   fp `edge` (без X25519MLKEM768). Сервер отдал маску — правило долей подтверждено с
   клиентской стороны: попытки отличаются одной долей. Это делает первый кейс MVP
   «подтверждённым» без сервера (в проекте было «вероятно»). Стоит третий TLS бюджета; если
   слота нет — спрашивает, ждать ли, или пропускает.
2. **Версия эталонного ядра — Xray v26.7.28** (`landscape.md`: «рабочий откат», собран Go 1.26,
   без #6797). Модуль `xtls/reality` поднят до 8cdf7bf (v26.9.9) — им тестовый сервер в
   `internal/sim` применяет правило X25519MLKEM768; клиентская часть REALITY — в самом Xray-core.
3. **xmux эталона задан явно** (`maxConcurrency`): по умолчанию XHTTP открывает отдельное
   TLS-соединение на каждую из первых `maxConnections` сессий — это лишние TLS к серверу сверх
   бюджета. Тест проверяет: одна проба = одно TLS-соединение.
4. **Все сокеты эталонного ядра — через диалер приложения** (`UseAlternativeSystemDialer`):
   бюджет списывается по факту соединения, а не по оценке; сокеты к серверу привязываются к
   физическому адаптеру (IP_UNICAST_IF), если маршрут по умолчанию ушёл в TUN клиента; по
   байтам видна стадия обрыва. Пробы P1/P2/N1–N4 привязываются так же.
5. **Служба Hiddify — `HiddifyTunnelService`** (по исходнику установщика v4.1.2), не
   `HiddifyService`; проверяются обе.
6. **Ошибка x509 у эталона = «маска»** (`real_cert`): Xray проверяет настоящий сертификат,
   если REALITY не узнал клиента; при невалидном сертификате маски строки
   `received real certificate` нет, есть x509. В обоих случаях аутентификации REALITY не было.
7. **Порт сервера** в окне и экспорте показывается, только если он 443; нестандартный порт —
   данные установки (AGENTS.md сервера), хранится лишь в DPAPI-файле сеанса.
8. **Контракт без JSON Schema-библиотеки:** проверка — по `schema.major` и обязательным полям в
   Go-структурах (`internal/bridge/contract.go`); `contracts/*.schema.json` появятся вместе с
   этапом 0 в `xray`.
9. **Окно без CLI Wails:** фронтенд — статические HTML/CSS/JS без сборщика, встраиваются
   `embed`; сборка `go build -tags desktop,production`. DPI-осведомлённость включается кодом;
   иконка, манифест и версия файла — go-winres в CI (`build.ps1` — локально).
   Проверка ветки или PR на Windows — `try-pr.ps1 <номер PR|ветка>`: сборка CI этого
   коммита (через `gh` или `GH_TOKEN` — артефакты Actions без входа GitHub не отдаёт), иначе
   сборка из исходников через `build.ps1`; суммы — по `SHA256SUMS.txt`. Файлы `.ps1` — в
   UTF-8 с BOM: без него Windows PowerShell 5.1 читает кириллицу в ANSI и ломается на
   «кавычках» (тест в `internal/repocheck`).

10. **Исправления по живому запуску (2026-11-01, Windows 11, Hiddify 4.1.1, четыре сценария).**
    - Факты Windows не собирались ни разу: скрипт шёл в `powershell -Command -` через stdin,
      а PowerShell 5.1 читает stdin построчно, как консоль, — многострочный `try { … }` ждал
      пустой строки, и `ConvertTo-Json` не выполнялся («unexpected end of JSON input»). Теперь
      `-EncodedCommand`. Без фактов не было ни состояния клиента, ни привязки проб мимо TUN.
    - Бюджет проб был общим на все серверы и при каждом сеансе окна заново подмешивал в счётчик
      уже учтённые отметки из `budget.json` — второй сеанс подряд получал «пропущено: бюджет»
      без единой пробы. Теперь бюджет у каждого сервера свой (`Engine.Budget(ServerKey)`),
      восстановление идемпотентно, `budget.json` хранит отметки по серверам. В отчёте — расход
      за сеанс, а не с запуска окна.
    - Пауза бюджета до 65 с — автоматически, с отсчётом в окне; дольше — с согласия. Повтор P4
      не ждёт 30 с, если первая проба пропущена по лимиту. Нет проб к серверу — итог
      `unknown.budget` («Проверка не завершена»), а не «нужно окно сервера».
    - **C10 — запрос через сам клиент** (SOCKS5 на его локальный порт; в TUN без порта — по
      системному маршруту). Подключён ли клиент — по самому порту, без PowerShell. Итоги:
      `ok.client` (подтверждено: трафик идёт), `ok.idle` (клиент не подключён, сервер и профиль
      в порядке), `client.tunnel` (клиент «подключается», трафик не идёт, эталон проходит).
      `C10.outcome=ok` исключает причины «не подключается».
    - Порядок фазы 2: P1 → P3 (→ P3m) → P2 только если эталон не прошёл; TCP не установился —
      эталон и P2 не запускаются, сразу повтор P4. Удачный сеанс Hiddify: 3 TCP и 2 TLS вместо
      4 и 3 — два сеанса подряд укладываются в лимит.
    - Окно: крупный итог (цвет — работает/нет, уверенность — отдельной меткой), цепочка звеньев,
      полоса хода. **Отступление от «в окне — только метки» по просьбе владельца:** окно
      показывает имя профиля и адрес сервера в маске (`203.*.*.7`, домен — `v***.com`), как сам
      Hiddify. Только окно: в текст отчёта, экспорт и открытый индекс истории они не попадают
      (`report.Target`, тест `TestTargetWindowOnly`); имя хранится в DPAPI-файле сеанса.
    - На живой Windows и живом сервере эти правки не проверены: проверено тестами (симулятор
      REALITY, SOCKS5-«клиент») и окном в Chromium с подставным API.

11. **Скрин 5 (2026-11-01): «по SSH захожу, а Hiddify — „Подключение…“».** TCP до порта сервера
    молчал дважды, вердикт был «адрес недоступен (бан IP?)» — хотя SSH того же адреса работал.
    - **P6 — SSH-порт того же адреса**, если P1 — таймаут: одно TCP в бюджете сервера, до паузы
      P4 (время сеанса не растёт). Порт — из алиаса настроек (`ssh -G`, без подключения), иначе
      22; в улики не пишется. Баннер `SSH-` — соединение принял сам сервер. Отвечает (или RST) —
      `server.port.drop` (L4: файрвол сервера/хостера, порт Xray, старый порт в профиле;
      альтернатива — фильтр по порту), `path.ip.unreachable` исключён. Порт из алиаса тоже
      молчит — довод за «весь адрес». Мост, дошедший до сервера (ключ, sudo, xm без bridge),
      даёт то же: `S0.ssh=ok`.
    - **`path.port`** — «сеть режет порт» — только подтверждённо: P5 (из другой сети порт
      открыт) или окно сервера (SYN не доходит).
    - **N5 — SNI маски на чужом адресе**, если N4 молчит после ClientHello: тот же SNI на адрес
      открывшегося эталона. Тоже тишина — находка `path.sni` («с этой маской REALITY не
      пройдёт»), ответ есть — режут адрес маски, на REALITY не влияет. К серверу — ничего.
    - Возможные причины при найденной главной — в «Также найдено» («возможно»): Hiddify 4.x без
      X25519MLKEM768 всплывёт после починки порта.
    - Логи: `outbound direct … failed` Hiddify — отдельной строкой («прямые проверки, мимо
      сервера»), чтобы таймауты прямого выхода не читались как таймауты к серверу.
    - Не проверено на живой Windows и сервере: `ssh -G` на OpenSSH для Windows — по документации.

12. **Скрин 6 (2026-11-02): «из другой сети (даже из другого города) — разницы нет, галочка
    без толку».** Галочка «Я в другой сети» подменяла сетевые улики сеанса уликами прошлого,
    верила на слово, что сеть сменилась, а её результат (P5) не входил ни в одно правило:
    «молчит и оттуда» не меняло ни вердикт, ни совет «проверьте из другой сети».
    - **P5 — сам**: сеанс хранит отпечаток сети (`Secret.Network` — хэш MAC шлюза маршрута по
      умолчанию, без MAC — хэш адаптера; только в DPAPI-файле сеанса) и сравнивает P1/P3/P6 с
      последним сеансом к тому же серверу из другой сети за 3 часа. Улики сеанса не
      подменяются. Галочка и `--other-network` убраны.
    - **`server.unreachable`** (L4): порт молчит из двух сетей, SSH не отвечает или не
      проверен — провайдер ни при чём; альтернатива — блокировка адреса по всей стране (обе
      сети российские), различает проверка из-за рубежа или консоль хостера.
      `path.ip.unreachable` при этом не поднимается. В той сети SSH отвечал — `server.port.drop`
      (подтверждено).
    - **Состояние Hiddify его словами** (`C10.shows`): по `connection_button.dart` hiddify-app
      кнопка пишет «Подключение…», когда ядро запущено, а тест задержки выбранного сервера не
      дал результата. C10 повторяет этот тест — «URL проверки соединения» через локальный
      прокси Hiddify (`C10.test_url_ok`). C8 — «ядро запущено», а не «подключён». Трафик идёт,
      а URL проверки нет — `beyond.latency_url` и итог «тоннель работает».
    - Не проверено на живой Windows: `Get-NetNeighbor` для MAC шлюза и подписи Hiddify — по
      документации и исходнику.

13. **Скрин 7 (2026-11-02): Hiddify «Подключение…», TCP до порта есть, итог «Без окна сервера
    причину не назвать», а `ssh <алиас>` с ПК — таймаут.** Эталон (fp chrome, X25519MLKEM768
    есть) получил маску, обычный TLS с SNI профиля — сертификат другого сайта (`other_cert`),
    маска по своему адресу открывалась. Ни одно правило `other_cert` не читало: «профиль не
    принят REALITY» ждал `mask_cert`, и вывод упал в `unknown.need_window`, хотя цепочка под
    ним уже показывала красное звено «Профиль». SSH не проверялся: P6 шла, только когда порт
    сервера молчит, а алиас в настройках не был задан.
    - **`profile.stale`** (L5): P3 `real_cert` + P2 `other_cert` + N4 — сервер по адресу
      профиля маскируется не под SNI профиля: профиль устарел (переустановка, `xm set-sni`) или
      адрес у другой машины. Без N4 — «возможно». `profile.reality` при `other_cert` не
      поднимается (не дублирует). Проверено и на стенде: профиль с чужим ключом REALITY даёт
      ту же пару исходов.
    - **P6 и при открытом порте**, если эталон не прошёл и клиент не работает: можно ли войти
      на сервер. Только с известным портом SSH (порт 22 наугад при открытом порте ничего не
      доказывает). Порт — из алиаса настроек, а без него — из `~/.ssh/config`: `Host`, у
      которого итоговый `HostName` — адрес профиля (первое значение по порядку блоков, как у
      ssh; строки до первого `Host`, маски, отрицания, `Include`). Алиас настроек от другого
      сервера (его `HostName` — другой IP) для P6 не берётся.
      **Отступление от §8.1** («`~/.ssh` не читаются»): читается только `~/.ssh/config` и
      только строки `Host`, `Match` (граница блока), `HostName`, `Port`, `Include`; ключи и
      `known_hosts` — нет. Алиас и порт — только в памяти сеанса; в улики, отчёт и историю не
      попадают (в улике — лишь источник порта: `settings` / `config`).
    - **SSH молчит или отказывает при открытом порте** — находка `server.ssh.silent`, звено
      «Сервер» — «SSH недоступен». Мост (S1) и окно сервера (S3) отсюда невозможны: блок
      `unavailable` в `taxonomy.yaml` заменяет их проверкой K1 (веб-консоль хостера или SSH из
      другой сети; там — `xm doctor` и `xm uri`). Замена — в движке правил для всех гипотез и
      для `unknown.*`.
    - **Итог не спорит с цепочкой:** без названной причины, но с красным звеном — «Не
      работает: сбой на звене «…»», а не «Причина не найдена»; у звена-следствия — следствие
      чего («— следствие: сервер не принял профиль»).
    - **Логи клиента:** строки прямого выхода (`outbound/direct`, монитор `outbound direct…`,
      DNS прямых соединений) — только `direct_failed`, их таймауты больше не идут в
      «таймаут» (было «таймаут ×372» при сотнях таймаутов прямого DNS). К серверу добавлены
      EOF, обрыв (RST), отказ, x509. Строки через сервер не вытесняются прямыми (14 + 6).
      Сводка C6 — тремя группами: через сервер, сам клиент, мимо сервера.
    - **«Для точного ответа»** (`SessionData.Need`, тексты — `taxonomy.yaml: missing`): порт SSH
      неизвестен, встроенная проверка Xray-core выключена при неработающем клиенте, логи
      клиента не найдены при неработающем клиенте. Только когда недостающее изменило бы вывод;
      до трёх строк; при итоге «работает» — пусто. Обязательных настроек нет: SSH находится
      сам, без него вывод всё равно есть.
    - **Ping (ICMP) не добавлен:** TCP до самого порта (P1, с задержкой) строже, а ответ ICMP,
      когда TCP молчит, ничего не доказывает — его закрывают хостеры и сети, а стек TUN клиента
      может отвечать на ping сам.
    - Не проверено на живой Windows: разбор `~/.ssh/config` и `ssh -G` — по документации
      OpenSSH; строки логов Hiddify для соединений через сервер — по формату sing-box.

14. **Профиль не VLESS + REALITY (issue #15).** Профиль из настроек с `security=tls`/`none`
    (или не VLESS) брался в проверку, и `security.not_reality` / `protocol.not_vless` давали
    «Профиль испорчен при импорте», хотя профиль цел.
    - **`profile.unsupported`** (L5, сразу после `profile.missing`): «Профиль не
      поддерживается: VLESS + TLS — xdiag проверяет только VLESS + REALITY» (`C3.kind`), статус
      «Не проверено». `profile.import` — только адрес (`addr.empty|addr.format`).

15. **UDP через тоннель (issue #17).** Все пробы через тоннель были TCP (HTTP): DNS по UDP в
    TUN, QUIC, звонки и игры (UDP over VLESS / XUDP) не проверялись.
    - **B4**: после 204 и загрузки эталон шлёт один DNS-запрос по UDP к публичному резолверу
      (`through_tunnel.udp_dns` в `hosts.yaml`) через `core.Dial` с UDP-адресом; три отправки за
      6 с. На XHTTP запрос идёт по уже открытому соединению (xmux) — нового TLS нет; на raw TCP
      нужно новое соединение — через бюджет, не хватило — B4 не пишется.
    - **`beyond.udp`** (находка L6, `gate: P3.outcome=ok`): UDP режет сервер, а не клиент и не
      путь — эталон идёт мимо клиента, UDP — внутри TCP тоннеля.
    - Симулятор: DNS-резолвер по UDP за тоннелем, `sim.StartWith(Options{BlockUDP: true})` —
      сервер отправляет UDP в blackhole.

16. **ADR: нестабильность во времени — обрывы, потери, скорость (2026-11-03, issue #16).**
    - **Контекст.** Сеанс разовый, через тоннель — один запрос и ≤ 64 КБ: периодический обрыв,
      которого нет в момент сеанса, не виден, а сеанс во время обрыва ловит его случайно.
      Постоянные пробы к серверу запрещены бюджетом (приложение C): частые соединения к одному
      адресу — сами паттерн для ТСПУ.
    - **Решение: только пассивные источники и журнал сервера, ни одной новой пробы.**
      1. **S2 — `xm health` (основной).** Сервер раз в 5 минут ставит окну вердикт
         (`ok | server | freeze | degraded | suspect | nodata | monitor`) по своей самопроверке и
         tcp_info соединений клиентов. Через мост — после этапа 0 в `grokki91/xray`; уже сейчас —
         импорт `health.json` (`sudo xm health --json`). Берутся инциденты за 24 ч по классам:
         `server` — сбой самого сервера, `freeze` — заморозка соединений, `degraded`/`suspect` —
         прочее (пока без правила); `nodata`/`monitor` — не сбой.
      2. **C6 — логи клиента за сутки (на ПК, без сети).** Строка со временем в начале (sing-box
         `+0300 2026-…`, Xray `2026/…`, приложения `[2026-…]`/ISO; без пояса — местное время) —
         отметка. **Серия** — ≥ 5 сбоев соединения через сервер (таймаут, обрыв, EOF, отказ,
         x509, REALITY) без разрыва дольше 5 минут: одиночный таймаут — обычно сайт за тоннелем.
         Прямой выход (`outbound/direct`, `dns-direct`) и ошибки самого клиента (ядро, TUN, порт)
         в хронологию не идут. «Восстановился» — запись без сбоев не раньше 5 минут после серии.
         В улики — только числа (`episodes`, `recovered`, `span_h`, `last_episode_min`), не время.
      3. **Сверка C6 × S2.** Серия совпала с инцидентом — окно сервера пересекает серию с
         допуском одного окна (5 минут); время ПК переводится в часы сервера по сдвигу из фактов
         (S1 `time_offset_s`). Факты S2: `overlap`, `overlap_server|freeze|other`,
         `day_server|freeze|other`.
    - **Выводы (только находки — итог «работает/не работает» они не меняют):**
      - `unstable.drops` — «возможно»: серия, после которой клиент работал; «вероятно»: ≥ 2 серии
        и сейчас тоннель проходит (C10 или эталон) либо клиент восстанавливался; «подтверждено»:
        серия совпала с инцидентом сервера и сейчас тоннель проходит — обрыв виден с двух сторон.
      - `server.episodes` — «вероятно»: серия совпала с окном `server`; «возможно»: окна `server`
        за сутки без логов клиента.
      - `path.freeze.episodes` — gate `N1.ok`, альтернатива (потери у провайдера/хостера),
        не выше «вероятно»: серия совпала с `freeze`; при совпадении с `server` — исключена.
        «Подтверждено» — только окном сервера во время обрыва (S3) или другой сетью (P5).
    - **C10 сериями — отклонено.** Повтор запросов через уже открытый тоннель клиента кажется
      бесплатным, но каждое новое соединение клиент сам может отправить к серверу новым TLS (xmux
      XHTTP, свой mux Hiddify) — приложение их не видит и не учтёт в бюджете; серия запросов
      раз в N секунд — тот самый постоянный паттерн. Остаётся один C10 за сеанс.
    - **Скорость — не меряется с ПК:** честный замер — мегабайты, а предел приложения — 64 КБ.
      Деградация — окна `degraded` журнала здоровья (факт `overlap_other`, правила пока нет).
    - **Тоже отклонено:** фоновая «канарейка» на ПК (§13, п. 11 — отдельным решением), ICMP
      (ничего не доказывает, см. п. 13), события сна Windows (снимали бы альтернативу «сон ПК» —
      следующий шаг, без новых прав).
    - **Совет S2** («включить журнал здоровья») предлагается, пока журнала нет или он выключен.
    - Не проверено на живой Windows и сервере: форматы строк — по исходникам sing-box и Xray;
      есть ли время в экспорте логов Hiddify — не проверено; поля инцидентов — по
      `bridge.Health` (вывод `ui/health.py`).

17. **Скрин 8 (2026-11-03): шлёт ли клиент на сервер — видно с ПК, до окна сервера** (окно
    `xm doctor` владелец снял на другом сервере). **C11** — таблица TCP Windows
    (`GetExtendedTcpTable`, без прав) во время C10: ни одного соединения с адресом и портом профиля —
    `client.nosend` (L0, order 140); SYN без ответа — вторая попытка к P1; TCP есть — «адрес/порт
    недоступен» исключены; маршрут в чужой TUN и WARP «прокси поверх WARP» — без вывода. Профиль —
    тот, с чьим сервером клиент соединён; TLS клиента — в окне бюджета. `xm doctor` и мост с другого
    сервера не учитываются; «aborted by the software…» — обрыв по тишине, не RST. Не проверено на
    живой Windows: таблица — по документации Microsoft, ключи WARP — по исходнику hiddify-app v4.1.1.

18. **Мост — часть диагностики, если SSH сервера профиля задан** (скрин 9: ключ под паролем).
    Алиас — из «Настроек», если ведёт на сервер профиля, иначе `Host` с его адресом (только имя).
    Отступление от §4.1: `facts` — до фазы 1; мост не готов (ключ, пароль ключа — `ssh -v` «Server
    accepts key», sudo, xm, чужой алиас) — сеанс не начинается, окно ведёт в «Настройки». SSH не
    дошёл — улика, под TUN — нет. Не проверено на Windows: `ssh -v` и ssh-agent — по документации.

19. **Пароль ключа SSH — в «Настройках»** (просьба владельца вместо ssh-agent). Отступление от §8.3:
    пароль хранится в vault (DPAPI) и отдаётся ssh.exe помощником `SSH_ASKPASS` (тот же exe, пароль —
    в окружении, не в командной строке); вместо BatchMode — `PasswordAuthentication=no`,
    `KbdInteractiveAuthentication=no`, одна попытка; помощник отвечает только на «passphrase for».
    Проверено на OpenSSH 9.6 (тест со sshd); `SSH_ASKPASS` у OpenSSH для Windows — не проверен.

20. **Hiddify 5.x (с v5.2.0, 2026-10-30) шлёт X25519MLKEM768** — `compat.yaml`: `mlkem: true`. Ядро
    (hiddify-sing-box 7d1760f в v5.2.0, 1614c5e в v5.5.5, `common/tls/h_reality_hello.go`) ставит
    её перед X25519 при любом fp, поэтому у чужих ядер `CX.fp_mlkem` берётся из таблицы ядра, а не
    из пресета, и P3m не идёт. Каталог данных v5.5.5 по исходнику тот же (`configs\<id>.json`,
    `shared_preferences.json`). Не проверено на машине: ни ClientHello, ни адаптер на 5.x.

## Контракт хэшей профиля (для `xm bridge facts`)

Соль — 16 случайных байт сессии, на сервер уходит hex (32 символа) через stdin. Хэш —
`HMAC-SHA256(соль, значение)`, первые 12 hex-символов; пустое значение — пустая строка.
Значения перед хэшем (`internal/profile.Hashes`), сервер обязан нормализовать так же:

| Поле `profile` | Значение |
|---|---|
| `clients.<имя>` | UUID клиента: нижний регистр, без пробелов по краям |
| `pbk` | публичный ключ REALITY (base64url, как в URI `pbk=`) |
| `short_ids[]` | shortId: нижний регистр; пустой shortId — пустая строка в списке |
| `path` | путь XHTTP как есть (`/…`) |
| `sni[]` | serverName: нижний регистр |
| `port` | публичный порт десятичным числом |

## Хранение и просмотр данных

Всё, что идентифицирует установку (профиль `vless://`, SSH-алиас, папки клиентов, сеансы с
адресом сервера и SNI), лежит только в `%LOCALAPPDATA%\xdiag` и только под DPAPI текущей
учётной записи. Посмотреть руками: `xdiag data show`, вкладка «Данные» → «Показать
сохранённые данные», либо PowerShell без xdiag (команда — в `README.txt` этого каталога).
В окно, отчёт и экспорт попадают только метки (`[server]`, `[sni]`, `[uuid:…]`, `[ip:A]`).
