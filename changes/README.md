# Файлы изменений — номер версии xdiag

Номер версии (`major.minor.patch`, начало — `1.0.0`) нигде не записан руками: его считает
`go run ./cmd/version` при сборке по файлам этого каталога. Каждый PR, который меняет
приложение (`cmd/`, `internal/`, `rules/`, `go.mod`; кроме одних тестов), добавляет **свой**
файл — CI без него PR не пропускает.

## Файл

`changes/<ветка>.md` — имя по последней части имени ветки
(`claude/affectionate-brahmagupta-iwzz89` → `changes/affectionate-brahmagupta-iwzz89.md`).

```
patch
- поле «Алиас» не теряет фокус при проверке
```

Первая строка — уровень, дальше — что изменилось (1–3 пункта, как в описании PR):

| Уровень | Когда | Пример |
|---|---|---|
| `patch` | исправление, мелкая правка текста, вида, правила | 1.4.2 → 1.4.3 |
| `minor` | новая возможность, вкладка, проверка, причина в правилах | 1.4.2 → 1.5.0 |
| `major` | несовместимо: формат сохранённых данных, контракт моста (`schema.major`) | 1.4.2 → 2.0.0 |

Один PR — один файл; если PR растёт, уровень в файле можно поднять. Уже слитые файлы не
переименовывать, не удалять и не править уровень: номер main только растёт.

## Почему без конфликтов

Общего файла с номером нет: две параллельные сессии добавляют разные файлы. Порядок — по
слиянию в main (первые родители истории git), изменения ветки — после изменений main:

- обе ветки от `1.0.0` с `patch` показывают `1.0.1`; сборка CI для PR (merge-коммит)
  показывает номер «как после слияния»;
- после слияния обеих main — `1.0.2`, без ручных правок перед мержем.

Нужна полная история git (`fetch-depth: 0`); с обрезанной номер — `dev`.

```bash
go run ./cmd/version -changes    # номер и все изменения по порядку
```
