# xray_client (xdiag) — инструкции для агентов

xdiag — приложение для Windows 11: по кнопке объясняет, почему VPN-клиент (Hiddify, v2rayN;
ядра sing-box и Xray) не подключается к серверу VLESS + REALITY (XHTTP или TCP) или работает не
так: на каком звене, какая причина и с какой уверенностью, на каких уликах, какое минимальное
действие. Сервер — из `grokki91/xray` (команды `xm`), но xdiag работает и без него. Отвечать
на русском.

Приоритеты при конфликте: 1) глубина и достоверность диагностики; 2) не ухудшать соединение и
стабильность приложения; 3) точность первопричины; 4) минимализм архитектуры и интерфейса;
5) расширяемость: новый клиент или ОС — новый адаптер, а не правка ядра; 6) экономия ресурсов
и токенов; 7) простота сопровождения. Правка, которая не улучшает диагностику, стабильность,
расширяемость или сопровождение, не делается. Объём правки = объём задачи: без «заодно» и
переписывания работающего.

## Где правда

При расхождении верно: код и `rules/*.yaml` → `docs/implementation.md` (сделанное, отличия от
проекта, не сделанное) → `docs/architecture.md` (проект v0.1, не обновляется). Документы
читать по разделам, не целиком; в проекте: §1.2 — восемь «таймаутов», §1.5 — уровни L0–L6,
§6 — каталог проверок (ID улик), §7 — модель уверенности, приложение C — бюджет проб.

## Публичный репозиторий: данные установки — никогда

В код, комментарии, тесты, фикстуры, README, коммиты и PR не попадает ничего, что
идентифицирует установку владельца:

- IP сервера, хостер, домены владельца, SNI маски установки;
- UUID, ключи и shortId REALITY, путь XHTTP, URL подписки;
- фактические порты установки, если они не 443;
- вывод программ с ПК или сервера как есть (логи, `doctor.json`, дампы, скриншоты с адресами).

Примеры — `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (RFC 5737), `example.com`;
UUID в тестах — `00000000-0000-4000-8000-…`; ключи — сгенерированные для теста (как в
`internal/sim`). `go test ./internal/repocheck/` проверяет рабочее дерево: IP вне
документационных и частных сетей и UUID — провал. Убрать, а не обходить. Хук Claude Code
`.claude/hooks/commit-guard.sh` гоняет эту проверку перед `git commit`/`git push` — и на тексте
команды (сообщение коммита); тест хука — `internal/repocheck/hook_test.go`.

## Конфиденциальность в коде

- Всё, что показывается или сохраняется вне DPAPI, проходит `internal/redact`; новый вид
  секрета — регистрировать в редакторе (`Profile.Register`, `redact.Add`).
- Секреты на диске — только `store.SaveVault` / `SaveSession` (DPAPI). Открытым текстом —
  только `settings.json`, индекс истории и бюджет (без адресов).
- Секреты не передаются в командной строке процессов (видна всем): stdin, файл в каталоге
  данных или переменная окружения.
- В окне — только `textContent` (строки логов недоверенные).

## Сеть

- Бюджет приложения C: ≤ 3 TLS к серверу за 60 с, ≤ 6 TCP за 5 минут; любая новая проба к
  серверу — через `netprobe.Budget`, эталонное ядро — только через `refcore` (его сокеты идут
  через диалер приложения).
- Приложение ничего не меняет в системе: маршруты, DNS, файрвол, службы, профили клиентов.
- «Таймаут ≠ блокировка»: гипотеза `path.*` — только с `gate: N1.ok=true` и `alternative`;
  «подтверждено» — только окном сервера (S3) или другой сетью (P5). Загрузчик правил
  проверяет лишь `alternative`; остальное доказывает сценарий в `internal/rules/rules_test.go`.

## Правила и факты

- Причины, проверки и тексты — в `rules/*.yaml`, не в Go. Новый код — в `taxonomy.yaml`,
  гипотеза — в `hypotheses/`, сценарий — в `internal/rules/rules_test.go`.
- Версии клиентов, ядер и правила сервера — `rules/compat.yaml`; источник —
  `grokki91/xray` `.claude/skills/xray-dpi/references/landscape.md` (репозиторий публичный:
  `git clone --depth 1 https://github.com/grokki91/xray <каталог вне этого репозитория>`).
  Правка факта — с датой и источником, в обоих репозиториях.

## Ответ

- Коротко, тезисами; ход работы не пересказывать. После задачи — только непустые разделы:
  **Сделано**; **Улучшено** — что xdiag теперь скажет или покажет; **Проверка** — что прогнано
  и что проверить на живом (команда PowerShell и ожидаемый итог); **Проблемы** — нерешённое и
  каких данных не хватает для вывода. Изменений нет — так и сказать.
- Факт, вероятная причина и непроверенная гипотеза — раздельно; предположение за факт не
  выдавать.
- Нужны данные от владельца — одним списком и с тем, как их получить («Копировать отчёт»,
  `xdiag history export <ID>`).

## Версия приложения — с каждой правкой

Любой PR, меняющий приложение (`cmd/`, `internal/`, `rules/`, `go.mod`; одни тесты, документация
и `.claude/` — нет), добавляет **новый** файл `changes/<последняя часть имени ветки>.md`:
первая строка — `patch` (исправление, мелкая правка), `minor` (новая возможность) или
`major` (несовместимо: сохранённые данные, контракт моста), дальше — 1–3 пункта, что
изменилось. Формат и примеры — [changes/README.md](changes/README.md).

- Номер (`1.0.0` → `1.0.1` / `1.1.0` / `2.0.0`) считает `go run ./cmd/version` при сборке по
  порядку слияний в main; руками его не пишут нигде — ни в коде, ни в `winres.json`.
- Общего файла с номером нет, поэтому параллельные сессии не конфликтуют; перед мержем ничего
  не согласовывать. Уже слитые файлы `changes/` не трогать.
- CI (`go run ./cmd/version -check origin/main`) не пропускает правку приложения без файла.
- Номер виден в окне: «О программе» и внизу боковой панели; в терминале — `xdiag version`.

## Проверка перед коммитом

```bash
gofmt -l cmd internal rules      # пусто
go vet ./... && GOOS=windows go vet -tags desktop,production ./...
go test ./...                    # сетевой симулятор: REALITY-сервер Xray-core на петле
go run ./cmd/version -check origin/main -changes   # файл changes/ на месте, номер растёт
```

Тест доказывает эффект правки: с откаченной правкой он падает. Тест ради покрытия не пишется,
падающий не ослабляется; ожидание существующего сценария меняется только как осознанная смена
вывода — с причиной в отчёте. Поведение на живой Windows и живом сервере тестами не
доказывается — так и писать.
