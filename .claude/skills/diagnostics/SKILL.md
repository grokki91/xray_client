# Диагностика: от живого случая к правилу

Цель — чтобы на этом случае xdiag назвал звено, причину с уровнем, улики и минимальное
действие, а если без данных не назвать — какой проверки не хватает.

## Порядок

Вести по ходу работы; в отчёт — только итоги (AGENTS.md, «Ответ»):

```
- [ ] Данные случая собраны; чего нет — запрошено одним списком
- [ ] Сценарий из улик случая воспроизводит текущий вердикт
- [ ] Первопричина неверного вывода — один из четырёх видов (ниже)
- [ ] Минимальная правка, по возрастанию цены: текст → правило → условие запуска пробы → новая проба
- [ ] Сценарий падает без правки; ожидания остальных сценариев не тронуты; проб к серверу не больше
- [ ] implementation.md; README — если меняется видимое пользователю; compat.yaml — если это факт
- [ ] Отчёт: что xdiag скажет на этом случае теперь; проверка на живом
```

## Данные случая

- Главное — «Копировать отчёт» в окне или `xdiag history export <ID>`: улики, шаги, вердикт,
  строки логов — без секретов. Скрин показывает только итог и цепочку.
- Со слов владельца — то, чего нет в уликах: что пишет клиент; какая сеть (Wi-Fi, мобильная,
  другой город); что работает рядом (браузер через VPN, SSH к серверу, другой клиент); что
  менялось (сервер, профиль, версия клиента).
- С сервера, если там `xm`: `sudo xm doctor --live 60 --json` во время одной попытки клиента —
  стадия и решение REALITY со стороны сервера, то есть «подтверждено».
- В репозиторий идёт не отчёт и не логи, а сценарий из улик (метки, RFC 5737).

## Сценарий и первопричина

Улики отчёта → случай в `TestScenarios` (`internal/rules/rules_test.go`: `with(…)`,
`ev(ID, ключ, значение, …)`) с ожидаемым кодом и уровнем; прогон показывает текущий вердикт и
«возможно». Ключи и значения улики — там, где она кладётся: `grep -n 'ID: "P3"'
internal/engine/*.go`. Виды первопричины:

1. **Наблюдения нет** — проба не шла или шла не в том случае → условие запуска в
   `internal/engine`; новая проба — только если ни одна собранная улика не различает гипотезы.
2. **Наблюдение есть, правило его не читает** — новое значение исхода, ключ без гипотезы →
   гипотеза или исключение.
3. **Срабатывает не то правило** — `order`, `gate`, слишком широкий `excluded`, уровень.
4. **Вывод верный, текст вводит в заблуждение** — только `title`, `why`, `alternative`,
   `actions`.

Как писать правила и пробы — `.claude/rules/diagnostic-rules.md` и `.claude/rules/probes.md`
(подгружаются при правке этих файлов).

## Принципы вывода

- Вывод — только из улик; признак — наблюдение, а не поле конфига, где следствие наблюдаемо.
- Сравнение с эталоном: сервер ↔ эталонный хост; SNI маски на адресе сервера ↔ на адресе
  маски; клиент ↔ эталонное ядро с тем же профилем; эта сеть ↔ другая. Различие — улика,
  совпадение снимает гипотезу.
- Уровни — по шапке `rules/hypotheses/base.yaml`. Наверху — одна причина, первая по стеку;
  остальное — «также найдено», «возможно», «исключено».
- Недостоверное доступными средствами (`docs/architecture.md` §6.7) так и называть: бан IP,
  белый список и роутер различает только другая сеть; заморозку по отпечатку и по SNI — время
  и другая сеть; антивирус и WFP — только «возможно». Чего xdiag пока не видит —
  `docs/implementation.md`, «Не сделано».

## Ловушки — каждая уже стоила разбора

- Проба, исход которой ничего не доказывает, не делается и в довод не идёт: ping при молчащем
  TCP (ICMP закрывают, TUN клиента отвечает сам), порт 22 наугад при открытом порте сервера.
- Каждое значение исхода пробы читает хотя бы одна гипотеза — иначе вывод падает в
  `unknown.*`, хотя цепочка уже показывает сбой (так было с `other_cert` до `profile.stale`).
- Итог и цепочка звеньев не спорят: красное звено — «не работает», а не «причина не найдена».
- Наблюдение сильнее таблицы версий и логов: трафик через клиент идёт (`C10.outcome=ok`) —
  причины «не подключается» исключены; таблица версий без эталона — не выше «возможно».
- Измеримое не спрашивать у пользователя: другую сеть узнаёт отпечаток шлюза, а не галочка;
  состояние клиента — запрос через его прокси (C10).
- Сделанную проверку не советовать снова; невозможную — заменять (`unavailable`: SSH молчит —
  веб-консоль хостера вместо моста).
- Строки логов клиента — по маршруту: прямой выход и DNS мимо сервера — не сбой сервера. Нет
  логов — не значит нет ошибок: Hiddify 4.1.x часто не пишет их на диск.
- x509 у эталона — тоже маска: REALITY клиента не узнал.
- Слова интерфейса клиента — по его исходнику: «Подключение…» в Hiddify — ядро запущено, а
  тест задержки по «URL проверки соединения» не прошёл.
- Проверяемый профиль не обязательно выбран в клиенте (в Hiddify — первый VLESS + REALITY
  активного профиля, если клиент сейчас не соединён ни с одним его сервером): при «эталон прошёл,
  клиент нет» это — в `alternative`.
- Шлёт ли клиент к серверу — наблюдение на ПК, а не догадка по окну сервера: таблица TCP Windows
  во время C10 (C11). Нет соединения — причина в клиенте, окно сервера ничего не покажет; SYN без
  ответа или TCP есть — «клиент не шлёт» исключено.
- Окно сервера — только с сервера профиля: серверов у владельца несколько, и окно снимают не там
  (так было на скрине 8). Адрес в `doctor.json` сверяется с адресом профиля; чужое не учитывается.
- «An established connection was aborted by the software in your host machine» (WSAECONNABORTED) —
  не RST: Windows закрыл соединение, когда сервер перестал подтверждать данные. RST — «forcibly
  closed by the remote host»; строки 127.0.0.1 ↔ 127.0.0.1 — приложение и прокси клиента.
- «Ключ не принят» у моста, а `ssh <алиас>` в терминале входит после пароля — ключ под паролем:
  BatchMode его не спросит. Различает `ssh -v` («Server accepts key» перед «Permission denied»);
  лечится ssh-agent, xdiag паролей не берёт.
- ssh.exe не привязан к физическому адаптеру, как пробы: под TUN клиента мост идёт в тоннель — его
  таймаут не улика о SSH сервера.
- Алиас моста в «Настройках» один, а серверов несколько: мост — к серверу профиля, по `Host` с его
  адресом в `~/.ssh/config`; чужой алиас без своего `Host` — сеанс не начинается.
- Бюджет TLS — на адрес сервера, а не на xdiag: хендшейки самого клиента в ту же минуту — в счёт
  («заморозка по отпечатку» считает все хендшейки с ПК).

Новый обобщаемый урок — строкой сюда, в той же правке.

## Факты извне

- Свежесть: `updated` в `rules/compat.yaml` старше 3 месяцев или вопрос о новой версии —
  сверить с первоисточником и с `landscape.md` сервера (AGENTS.md, «Правила и факты»).
- Первоисточники: XTLS/Xray-core и XTLS/REALITY (код, releases, issues), SagerNet/sing-box,
  hiddify/hiddify-app и её ядро, 2dust/v2rayN (wiki, issues), документация Microsoft. Форум и
  чат — «по отчётам», со ссылкой, но не факт.
- Поведение клиента — по исходнику (файл и коммит), а не по скрину; не проверено на машине —
  так и пометить.
- Режим цензора и проверка, отличающая его от сбоя, — `landscape.md`, «Цензор (РФ)».

## Новый клиент или ОС

Адаптер — файл в `internal/clients` (Detect, Profiles, Logs, State, Hints) или `internal/osw`;
версия и ядро — в `compat.yaml`; неизвестная версия — `support: partial`, остальные проверки
идут. Движок и гипотезы не меняются, кроме фактов `CX`. Тест — каталог-имитация с
обезличенными данными.

## Проверка на живом

CI собирает exe на каждый push (артефакт `xdiag-windows-amd64`). Владельцу в отчёте — одна
команда PowerShell (нужен `gh auth login`; без `gh` — PR → Checks → build → Artifacts):

```powershell
$b='<ветка>'; $id=gh run list -R grokki91/xray_client -b $b -w build -s success -L 1 --json databaseId -q '.[0].databaseId'; gh run download $id -R grokki91/xray_client -n xdiag-windows-amd64 -D "$env:TEMP\xdiag-$id"; & "$env:TEMP\xdiag-$id\xdiag-ui.exe"
```

и сценарий: что сделать (подключить клиент, выключить его, сменить сеть) → какой итог ждать в
окне и с каким кодом. Результат — «Копировать отчёт» в ответ; не совпал — это новый живой
случай.
