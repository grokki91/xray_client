# Правила диагностики: rules/*.yaml

Загрузчик (`internal/rules`) сам ловит код вне таксономии, дубль, предикат без ID улики,
`next_checks` вне каталога и `path.*` с «вероятно» без `alternative`. Ниже — то, что он
проверить не может.

## Гипотеза

- Код — в `taxonomy.yaml`. `order` — стек: интернет и профиль (100–110) → наблюдения сервера
  (150–157) → клиент (200–270) → Windows (280–298) → профиль (300–345) → путь (490–560) → за
  тоннелем (800+) → «работает» (897–900) → находки (950+) → `unknown.*` (989+). Вердикт —
  первая по `order` причина с «вероятно» и выше: выше ставить только то, без чего нижнее не
  важно.
- `kind`: по умолчанию причина; `finding` — не причина сбоя, но важно знать; `ok` — итог
  «работает» (берётся самый сильный).
- Уровни — по шапке `hypotheses/base.yaml`. «Подтверждено» — наблюдение с двух сторон (S1, S3),
  повтор из другой сети (P5) или контрольная пара попыток, отличающихся одним признаком (P3 ↔
  P3m, клиент ↔ эталон с тем же профилем). Таблица версий и слова пользователя без наблюдения —
  не выше «возможно».
- Гипотезы о пути и доступности сервера — с `N1.ok=true` (в `gate` или в каждой группе): без
  интернета нет ни блокировки, ни молчащего сервера. Гипотеза о пути называет режим цензора и
  проверку, которая отличит его от сбоя (`landscape.md` сервера, «Цензор (РФ)»).
- `excluded` — наблюдения, при которых гипотеза ложна: у причин «не подключается» —
  `C10.outcome=ok`, у причин до тоннеля — `P3.outcome=ok`. Исключение убирает гипотезу даже из
  «возможно» — шире доказанного не ставить.
- `alternative` — у каждого «вероятно», не подтверждённого с двух сторон: что ещё даёт ту же
  картину и какая проверка различит.
- Та же картина, что у соседней гипотезы, — уточнить условия, а не дублировать (как
  `!P2.outcome=other_cert` у `profile.reality`).
- `unavailable` — проверка, которую сейчас не выполнить, и её замена; `missing` — тексты «для
  точного ответа», условия к ним — в `internal/engine` (`r.missing`).

## Тексты — их читает пользователь

- `title` — одна строка: что сломано и где. `why` — механизм в 1–2 фразах, словами
  пользователя. `actions` — 1–3 шага, первый — самый вероятный и дешёвый; команда сервера —
  копируемая, с `sudo` и `<имя>`; путь в клиенте — как в его меню.
- Не лечится конфигом (бан адреса, белый список) — так и написать.
- Подстановки `{ID.ключ}` и `{COMPAT.recommend}`: нет улики — в тексте «?»; ключ брать из улики,
  которая есть в каждой группе, где гипотеза срабатывает.

## Проверка

- Правка условий — случай в `TestScenarios` (`internal/rules/rules_test.go`), который должен
  сработать, и ближайший, который не должен; имя — по случаю («скрин N: …»).
- `compat.yaml` — `updated`, источник у факта и та же правка в `landscape.md` сервера.
- `go test ./internal/rules/`, затем — по AGENTS.md.
